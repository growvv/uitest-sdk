# 15 · agent 任务成功率评测

问的是：「把 `uitest-phone` 交给一个 coding agent，它能在一台真机上把事做完吗？」
不是工具能不能调通（那是 `docs/acceptance/` 的单元验收），也不是一步多快（那是
`docs/benchmarks.md`）。这一页记口径、任务库怎么设计、判分怎么防作弊，以及第一轮的数字。

评测台在 `.work-bench/eval-phone/`（20 条）与 `.work-bench/eval-scale/`（1000 条），
两个目录都不入库：里面是跑批脚本和逐条日志，属于实验记录，不是产品代码。

## 口径

| 项 | 取值 |
|---|---|
| agent | Codex CLI（`codex exec`），通过 `uitest-phone mcp` 的 MCP 服务调用工具 |
| 设备 | 真机 MLR-AL10（tag `7544d645`），HarmonyOS 7.0.0.111 SP16，1600×2560 |
| 登录状态 | 未登录任何账号；任务只走不触发登录的路径 |
| 判分 | agent 收工后由评测脚本读设备，**不看 agent 的自述** |
| 重试 | 单轮，不重试；一次失败就是一次失败 |
| 超时 | 单条 480 s |
| 允许的工具 | 只有 `uitest_*` MCP 工具；prompt 明确禁止 hdc、脚本、SDK 直连、浏览器 |

## 判据分三档

结构判据会把成功率抬高，所以三档分开统计，报告里也分开写。

| 判据 | 做法 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 内容（content） | 答案里必须有屏幕上才有的东西：价格、版本号、温度、计数 | 读对了内容 | — |
| 设备（device） | 收工后重新打开应用，滚动找 agent 声称创建/读到的条目 | 东西真的在设备上 | 过程是否合理 |
| 结构（shape） | 只要求答案里有 2 条以上列表项、长度够 | 到达了一个列表并读出了条目 | 读的是不是对的那个列表 |

1000 条任务库里：内容 796 条、设备核对 55 条、设备查找 36 条、结构 113 条。

## 跑批中途改过代码：三个分段

这一轮跑批跑着的时候，前 80 条里暴露的缺陷被边修边发，所以 1000 条**不是同一套二进制
跑出来的**。报数时按下面的时间点分开看，不要混成一个成功率：

| 段 | 起止（本地） | 当时的代码 | 条数 | 通过 |
|---|---|---|---|---|
| A | 11-20 05:07 – 08:24 | `launch` 只匹配 bundle id；`entryAbility` 不优先 launcher ability | 61 | 58 |
| B | 08:24 – 09:07 | 上面两处已修，skill 已刷新；`launch` 工具描述还是旧的一句话 | 19 | 18 |
| C | 09:07 – 10:10 | 工具描述也修了（见下） | 20 | 15（另 3 超时、2 失败） |
| D | 10:10 – 12:05 | 加上 `type --clear`（清空走设备句柄，输入走坐标） | 33 | 30（另 3 超时） |
| E | 12:05 – 12:29 | `--clear` 的清空与输入走同一组件句柄；ref 失配先等屏幕稳定再看一次（12:13 构建把 `tap` 也加上） | 4 | 4 |
| F | 12:29 – 12:45 | `--clear` 丢控件不再抛异常：动态 id 的输入框退到坐标输入 | 2 | 0（两条超时） |
| G | 12:45 起 | 桌面图标显示桌面上的应用名，不再显示 bundle 转储 | 进行中 | — |

分段按**开始时间**切（`results.json` 里 `at - ms`）：每条任务在自己开始时起一个 MCP
进程，那时加载的代码就是它整条用的代码。jd-07 就是一个例子——12:02 开始、12:10 结束，
看起来在 E 段，实际用的全是 D 段代码。

A 段的 3 条失败全是 notepad，原因都是 agent 没读 skill、去点标签为 bundle 转储的桌面
图标。B 段的 1 条失败是 notepad-04，原因相同——**修 skill 只影响会读 skill 的那 45%**。
C 段改成修 MCP 工具描述，这是 100% 的 agent 都看得到的。C 段的 2 条失败都不是工具的错：
clock-05 是判分器的 bug（答案全对却被数成 2 条，已修，见 `docs/14`），files-05 是超时。

**重建对正在跑的批是立刻生效的。** codex 的 MCP 配置指向 `packages/phone/dist/bin.js`，
每条任务起一个新的 MCP 进程，所以 `npm run build` 之后的下一条任务就是新代码。
D 段的第一条用上 `--clear` 的实测是 files-05（10:11）：`type --ref 23100 --text 图库
--clear` → `settled`，搜索框里是「图库」而不是追加后的旧值。它最后还是超时了，
但超时的原因是它一直在找「图库」那一行的日期与项数——那个页面上根本没有，
与 `--clear` 无关。

**D 段的 `--clear` 成功了 10 次、失败了 18 次**（28 次带 `clear` 的 `type`）。失败里
10 次是 `not_found · ref N`——ref 是 agent 的 `observe` 刚打印出来的；6 次是
`the field holds ""`，即清空之后字没落到框里。两条都指向同一个实现问题：清空会让输入框
丢焦点，随后按坐标的 `Driver.inputText` 就输到了页面上（books-05、settings-05）；而
ref 失配全部发生在 tap 之后、键盘滑入的那一秒里，紧跟着的同一句调用却能成功——所以
E 段把清空和输入改到同一个组件句柄上，并让 ref 失配先等屏幕稳定再看一眼。
**这一条也要写进验收报告：D 段的 91% 不是 `--clear` 的功劳，它当时成功不到四成。**

F 段两条。notepad-07（12:35 开始）：它把 ref 29259 当成备忘录点了，实际打开的是
**`com.huawei.hmos.hinote`（笔记）**——该 ref 的标签是
`AppIcon Image com.huawei.hmos.hinoteHiNotePcMainAbilityHiNotePc0 undefined 1`，桌面图标
的 bundle 转储里没有一个字能让人读出「笔记」还是「备忘录」。它随后在 hinote 里新建
「评测笔记 07」、写正文、连按三次返回，超时。这是 notepad-01..05 的同一根因，也是
G 段修的东西：屏幕模型给这类图标显示桌面上的名字（一次 `bm dump -a -l`，只在屏幕上真有
转储时才取）。

另一条是 clock-07（12:38 开始），与工具无关：它在闹钟的时间选择器上「研究」了八分钟
（日志里的 reasoning 原话是 “Investigating minute selection mechanics”），18 次调用
全是 swipe 和 observe 的交替，480 s 到点时还在组滑动手势。任务本身是只读的（读世界
时钟/闹钟列表），它自己走进了编辑闹钟的路径。**这是 agent 的失败，不是工具的失败**——
同一屏上 `swipe` 每次都返回了新布局，工具没有卡住。

E 段还暴露了第三种失败形状（meituan-07，12:26）：`Component.clearText` 抛异常——
`Widget: … id; value:1795148153645 … does not exist on current UI!(NoCandidates)`。
美团的输入框 id 是**动态的**，下一次布局就换一个，句柄在清空前就失效了。异常没有
被任何一层接住，整条 MCP 调用变成 `-32603`，agent 看不到状态词。修法是把清空整段
当尽力而为：控件没了就直接按坐标输入，回读照旧报框里的值。

**C 段的效果目前测不出来。** 用中文名 `launch` 的比例：A+B 段 33/79（42%），
C 段 3/8（38%）——样本太小。真正带来提升的是 08:24 的重建：中文名 `launch` 的成功率
从 16/28 升到 10/12（57% → 83%），因为 `resolveBundle` 之前根本不认识中文名。

**教训：** 边跑边修会让数据集分成几段。要么先把缺陷修完再开跑，要么一开始就接受
「分段报数」。这一轮是后者，数字要按表里的分段引用。

**判分器本身也是被测对象。** clock-05 答对了四个标签，被判「条目数 2 < 3」——判分器
把 agent 的开场白算成了一条，顿号切分没机会执行；而且它要求每段至少 4 个字，
「闹钟」「秒表」永远到不了。这条不是 agent 的失败，报告里要单列。**每一条失败都要
打开日志看一眼再归类**：工具失败、agent 失败、判分器失败，三种结论对产品意义完全不同。


## 任务库怎么设计

20 个应用 × 50 条。每个应用的任务按「能力面」铺开，而不是把同一件事重复 50 次：

| 应用 | 覆盖的面 |
|---|---|
| 计算器 | 50 道四则运算，覆盖四种运算符与多位数 |
| 设置 | 50 个设置项，读开关状态/容量/版本号 |
| 微博 / 知乎 | 分类浏览、搜索、逐条滚动读取、详情页计数 |
| 淘宝 / 京东 / 拼多多 | 搜索、价格排序、商品详情、加入购物车、首页滚动 |
| 美团外卖 / 大众点评 | 搜索店铺、评分、起送价/人均、分类频道 |
| 高德地图 | 地点搜索、公交/驾车路线（登录墙已标注） |
| 备忘录 / 时钟 | 新建条目并在列表里核对（写类任务，判据在设备上） |
| 文件管理 / 天气 / 阅读 | 目录浏览、城市切换、温度与预报、书名与简介 |
| 电话 / 信息 | 拨号盘、五个分页、空状态、新建短信页的收件人/正文/附件 |
| 日历 | 年/月/周/日四种视图各自的结构、翻页、今天、农历与节气 |
| 相机 | 五个模式、变焦档位、左侧工具栏、设置页 |

第一版任务库有 205/1000 条是重复填充（日历 74%、相机 66%、联系人 52%、信息 50%），
同一句话只换个序号——那不是覆盖功能，只是把同一个动作重复 50 次。按真机实际界面重写后
降到 69 条。这 69 条又逐条改写掉了：剩下的重复不是「多轮验证」，是同一个任务跑两遍——
`zhihu-41` 和 `zhihu-46` 一字不差，两条都通过只会让成功率好看一点，不会多测出任何东西。
现在 1000 条提示语互不相同（`audit.ts` 报 0 条重复），也没有一条内容判据只靠 `\d`、`.`、
`\S` 这种什么都能匹配的模式（`weak.ts` 报 0 条）。

重写时先逐页 `observe` 真机，按屏幕上真实存在的东西出题：联系人和信息在这台设备上是空的，
空状态本身就是答案；日历有四种布局；相机有模式条和变焦档位；文件管理的首页每行带日期与项数。
同一个界面上值得读的地方往往不止一处，所以「一个频道一条」改成「一个频道两条」——先读第一个
推荐项，再读这个频道自己的筛选栏，两条问的不是同一件事。

写类任务会改设备状态，所以：

- 时钟的闹钟建完立刻关掉开关，或改用世界时钟（只读且会留存）——跑批要几天，
  一个开着的闹钟会在别人的任务中途响。
- 备忘录创建的笔记会留存，这是刻意的：判据就是「列表里有这条」。
- 购物类只加购不下单，prompt 明确禁止点「立即购买」「提交订单」「付款」。

## 防作弊

- **编造的标题过不了。** 微博/知乎的「读出第 N 条标题」用设备判据：把 agent 报的标题
  拿回手机上滚动找，找不到就是失败。模型没法凭空编一个屏幕上存在的字符串。
- **说做了不算做了。** 备忘录、闹钟、世界时钟的判据是重新打开应用滚到那条为止。
- **不许绕过工具。** prompt 禁止 hdc / 脚本 / SDK；每一条 MCP 调用都落在
  `out/logs/<task>.jsonl`，事后可以数调用次数和报错次数。

## 第二轮：1000 条（进行中）

20 应用 × 50 条。断点续跑：每条完成即写 `out/results.json`，中断后重跑跳过已完成的 id。

```bash
# 全量（跳过已完成的）
npx tsx .work-bench/eval-scale/run.ts

# 单个应用 / 单条 / 前 N 条
npx tsx .work-bench/eval-scale/run.ts --app weibo
npx tsx .work-bench/eval-scale/run.ts --only calc-01
npx tsx .work-bench/eval-scale/run.ts --limit 20

# 重跑一条已完成的
npx tsx .work-bench/eval-scale/run.ts --redo weibo-05

# 出报告
npx tsx .work-bench/eval-scale/report.ts
```

单条实测 30 s–8 min（中位约 2 min），串行跑完约 30–40 小时。跑批期间不要并发跑别的
设备命令：两次 `captureLayout` 会撞在 agent 的全局锁上，任务会被记成设备不可用。

**收批后要重跑的失败。** 下面这些条目跑在修复之前，它们的「失败」不能留给最终报告：

| 条目 | 为什么重跑 |
|---|---|
| meituan-05、meituan-06 | 卡片标签截断修复之前跑的超时；meituan-07 修后 12 次调用通过 |
| notepad-01..05 | `launch` 工具描述修复之前；重跑才能看出「不读 skill 的 55%」有没有被覆盖 |
| zhihu-07、jd-07 | `--clear` 与 ref 稳定化之前；这两条是 E 段修复的直接证据 |
| files-05 | agent 在页面上找一个不存在的字段；看新版会不会更快放弃 |
| dianping-05 | 页面 settle 超时 + 路线绕远，不含已修的缺陷，重跑确认是否稳定复现 |

clock-05 不用重跑：它答对了，是判分器判错（已修），在报告里按通过计。

**跑批顺序是轮转的，不是按应用排的。** 30 多小时必然会被打断，按应用排的话跑到第 6 小时
只有 6 个应用有数据、另外 14 个一片空白；轮转后第一个 20 条就覆盖全部 20 个应用，任何
中断点都是一个二十个应用的样本。每轮每个应用出一条，各应用内部保持自己的顺序，所以续跑
会接着上次的位置往下走，不会从头再转一圈。
