# 15 · agent 任务成功率评测

问的是：「把 `uitest-phone` 交给一个 coding agent，它能在一台真机上把事做完吗？」
不是工具能不能调通（那是 `docs/acceptance/` 的单元验收），也不是一步多快（那是
`docs/benchmarks.md`）。这一页记口径、任务库怎么设计、判分怎么防作弊，以及第一轮的数字。

评测台在 `.work-bench/eval-phone/`（20 条）与 `.work-bench/eval-scale/`（1000 条），
两个目录都不入库：里面是跑批脚本和逐条日志，属于实验记录，不是产品代码。

## 口径

| 项 | 取值 |
|---|---|
| agent | Codex CLI（`codex exec`），通过 `uitest-phone mcp` 的 MCP 服务调用工具 |
| 设备 | 真机 MLR-AL10（tag `7544d645`），HarmonyOS 7.0.0.111 SP16，1600×2560 |
| 登录状态 | 未登录任何账号；任务只走不触发登录的路径 |
| 判分 | agent 收工后由评测脚本读设备，**不看 agent 的自述** |
| 重试 | 单轮，不重试；一次失败就是一次失败 |
| 超时 | 单条 480 s |
| 允许的工具 | 只有 `uitest_*` MCP 工具；prompt 明确禁止 hdc、脚本、SDK 直连、浏览器 |

## 判据分三档

结构判据会把成功率抬高，所以三档分开统计，报告里也分开写。

| 判据 | 做法 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 内容（content） | 答案里必须有屏幕上才有的东西：价格、版本号、温度、计数 | 读对了内容 | — |
| 设备（device） | 收工后重新打开应用，滚动找 agent 声称创建/读到的条目 | 东西真的在设备上 | 过程是否合理 |
| 结构（shape） | 只要求答案里有 2 条以上列表项、长度够 | 到达了一个列表并读出了条目 | 读的是不是对的那个列表 |

1000 条任务库里：内容 786 条、设备核对 55 条、设备查找 36 条、结构 123 条。

## 任务库怎么设计

20 个应用 × 50 条。每个应用的任务按「能力面」铺开，而不是把同一件事重复 50 次：

| 应用 | 覆盖的面 |
|---|---|
| 计算器 | 50 道四则运算，覆盖四种运算符与多位数 |
| 设置 | 50 个设置项，读开关状态/容量/版本号 |
| 微博 / 知乎 | 分类浏览、搜索、逐条滚动读取、详情页计数 |
| 淘宝 / 京东 / 拼多多 | 搜索、价格排序、商品详情、加入购物车、首页滚动 |
| 美团外卖 / 大众点评 | 搜索店铺、评分、起送价/人均、分类频道 |
| 高德地图 | 地点搜索、公交/驾车路线（登录墙已标注） |
| 备忘录 / 时钟 | 新建条目并在列表里核对（写类任务，判据在设备上） |
| 文件管理 / 天气 / 阅读 | 目录浏览、城市切换、温度与预报、书名与简介 |
| 电话 / 信息 | 拨号盘、五个分页、空状态、新建短信页的收件人/正文/附件 |
| 日历 | 年/月/周/日四种视图各自的结构、翻页、今天、农历与节气 |
| 相机 | 五个模式、变焦档位、左侧工具栏、设置页 |

第一版任务库有 205/1000 条是重复填充（日历 74%、相机 66%、联系人 52%、信息 50%），
同一句话只换个序号——那不是覆盖功能，只是把同一个动作重复 50 次。按真机实际界面重写后
降到 69 条，剩下的都是同一功能上的不同数据（备忘录搜同一关键词、阅读的不同分类），
保留是有意的多轮验证。重写时先逐页 `observe` 真机，按屏幕上真实存在的东西出题：
联系人和信息在这台设备上是空的，空状态本身就是答案；日历有四种布局；相机有模式条和
变焦档位；文件管理的首页每行带日期与项数。

写类任务会改设备状态，所以：

- 时钟的闹钟建完立刻关掉开关，或改用世界时钟（只读且会留存）——跑批要几天，
  一个开着的闹钟会在别人的任务中途响。
- 备忘录创建的笔记会留存，这是刻意的：判据就是「列表里有这条」。
- 购物类只加购不下单，prompt 明确禁止点「立即购买」「提交订单」「付款」。

## 防作弊

- **编造的标题过不了。** 微博/知乎的「读出第 N 条标题」用设备判据：把 agent 报的标题
  拿回手机上滚动找，找不到就是失败。模型没法凭空编一个屏幕上存在的字符串。
- **说做了不算做了。** 备忘录、闹钟、世界时钟的判据是重新打开应用滚到那条为止。
- **不许绕过工具。** prompt 禁止 hdc / 脚本 / SDK；每一条 MCP 调用都落在
  `out/logs/<task>.jsonl`，事后可以数调用次数和报错次数。

## 第二轮：1000 条（进行中）

20 应用 × 50 条。断点续跑：每条完成即写 `out/results.json`，中断后重跑跳过已完成的 id。

```bash
# 全量（跳过已完成的）
npx tsx .work-bench/eval-scale/run.ts

# 单个应用 / 单条 / 前 N 条
npx tsx .work-bench/eval-scale/run.ts --app weibo
npx tsx .work-bench/eval-scale/run.ts --only calc-01
npx tsx .work-bench/eval-scale/run.ts --limit 20

# 重跑一条已完成的
npx tsx .work-bench/eval-scale/run.ts --redo weibo-05

# 出报告
npx tsx .work-bench/eval-scale/report.ts
```

单条实测 30 s–8 min（中位约 2 min），串行跑完约 30–40 小时。跑批期间不要并发跑别的
设备命令：两次 `captureLayout` 会撞在 agent 的全局锁上，任务会被记成设备不可用。
